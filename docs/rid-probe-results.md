# ผล Probe API อ่างเก็บน้ำขนาดกลาง (RID)

ตรวจเมื่อ 24 ตุลาคม 2569 (2026-10-24) เวลาประมาณ 22:30 น. ICT ด้วย `scripts/probe_rid_api.py`
เอกสารนี้เป็นหลักฐานการสำรวจเพื่อ M3 ไม่อนุมัติการเผยแพร่ข้อมูล ไม่แก้ `config/sources.json`
หรือ `config/resource_licenses.json` และไม่บันทึกค่าตัวเลขของอ่างเก็บน้ำไว้ใน repository

ผลของ probe รอบนี้ยืนยันข้อสรุปใน [source-expansion-api.md](source-expansion-api.md) หัวข้อ RID
และเพิ่มข้อจำกัดด้านความถูกต้องของข้อมูลที่ต้องตรวจก่อนเชื่อมจริง

## 1. สรุปผลสั้น

| ประเด็น | ผลที่ตรวจจริง |
|---|---|
| anonymous access | ใช้งานได้ ไม่ต้องใช้ credential, ไม่ต้อง login |
| schema | JSON object ชั้นนอก 4 ฟิลด์ `document` `date` `total` `data` แล้วจัดกลุ่มแบบ `region` → `reservoir[]` |
| grain | 1 ระเบียนต่อ (วันที่รายงาน, รหัสอ่างเก็บน้ำ) อ่างทั้งหมด 461 แห่ง |
| พื้นที่ | มีแค่ 6 ภาคแบบ macroregion ไม่มีรหัสจังหวัด ไม่มีพิกัด ไม่มีลุ่มน้ำ |
| หน่วย | `storage` `dead_storage` `volume` = ล้าน ลบ.ม. (ล้านลูกบาศก์เมตร); `percent_storage` = ร้อยละ; `inflow`/`outflow` = ไม่มีหน่วยระบุ |
| query วันย้อนหลัง | รองรับ ผ่าน path `/public/YYYY-MM-DD` เท่านั้น ประวัติย้อนหลังได้ถึง 1998-01-01 |
| กับดักสำคัญ | วันที่ผิดแค่เดือน/วัน และวันที่ก่อน 1998 คืน HTTP 200 พร้อมรายงานอื่นแบบเงียบ ๆ |
| license | ไม่พบข้อความสิทธิ์/ลิขสิทธิ์/เงื่อนไขเผยแพร่ที่ใด → คงสถานะ `pending` |
| SWOC | เป็นคนละ API ต้องใช้ token ไม่มี credential ตอบ HTTP 401 |

## 2. Endpoint ที่ตรวจและวิธีเข้าถึง

| Endpoint | ผล |
|---|---|
| `GET https://app.rid.go.th/reservoir/api/reservoir/public` | HTTP 200, `application/json`, ~116 KB |
| `GET https://app.rid.go.th/reservoir/api/reservoir/public/YYYY-MM-DD` | HTTP 200, รายงานของวันนั้น |
| `GET https://app.rid.go.th/reservoir/api/document/reservoir` | HTTP 200, HTML ตารางฟิลด์และหน่วยอย่างเป็นทางการ |
| `GET https://swoc-api-service.rid.go.th/api/rsv-data/?date=...` | HTTP 401 เมื่อไม่ส่ง credential |

หมายเหตุจาก response header ของ endpoint สาธารณะ: `Access-Control-Allow-Origin: *` (เปิด CORS),
`Server: Microsoft-IIS/8.5`, `X-Powered-By` สองค่าคือ `PHP/7.2.15` และ `ASP.NET` และมีการออก `Set-Cookie` session ของ PHP
(ค่า cookie มี IP และ user agent ของผู้เรียก จึงไม่ควรบันทึกค่า cookie ลง repository)

**การยืนยันตัวตน:** probe รอบนี้ไม่ส่ง token, key หรือ cookie ใด ๆ และได้ HTTP 200
สิทธิ์เปิดใช้งานไม่เท่ากับสิทธิ์เผยแพร่ต่อ จึงยังไม่เปลี่ยนสถานะ `pending`

## 3. โครงสร้าง JSON

โครงสร้างที่ได้ (แสดงเป็น placeholder ไม่ใส่ค่าตัวเลขจริงของอ่างเก็บน้ำ):

```json
{
  "document": "https://app.rid.go.th/reservoir/api/document/reservoir",
  "date": "<YYYY-MM-DD วันที่ของรายงาน>",
  "total": "<int จำนวนอ่างเก็บน้ำทั้งหมดในรายงาน>",
  "data": [
    {
      "region": "<ภาค 6 กลุ่ม: ภาคเหนือ, ภาคตะวันออกเฉียงเหนือ, ภาคตะวันออก, ภาคกลาง, ภาคตะวันตก, ภาคใต้>",
      "reservoir": [
        {
          "id": "<รหัสอ่างเก็บน้ำ รูปแบบ rsv + ตัวเลข>",
          "name": "<ชื่ออ่างเก็บน้ำ ภาษาไทย>",
          "storage": "<float ความจุเก็บกัก ล้าน ลบ.ม.>",
          "dead_storage": "<float ความจุเก็บกักต่ำสุด ล้าน ลบ.ม.>",
          "volume": "<float ปริมาณน้ำในอ่าง ล้าน ลบ.ม. หรือ null>",
          "percent_storage": "<float เปอร์เซนต์ปริมาณน้ำต่อความจุ>",
          "inflow": "<float ปริมาณน้ำไหลเข้า หรือ null ไม่มีหน่วยระบุ>",
          "outflow": "<float ปริมาณน้ำระบาย หรือ null ไม่มีหน่วยระบุ>"
        }
      ]
    }
  ]
}
```

### 3.1 ฟิลด์และชนิดข้อมูลที่วัดได้ (รายงานปัจจุบัน 24 ต.ค. 2569)

| ฟิลด์ | ชนิดที่พบ | null | หมายเหตุ |
|---|---|---|---|
| `id` | str | 0 | 461 id ไม่ซ้ำ รูปแบบเดียว `rsv` + ตัวเลข |
| `name` | str | 0 | ชื่อไทยของอ่างเก็บน้ำ |
| `storage` | float/int | 0 | ไม่มีค่า 0 |
| `dead_storage` | float/int | 0 | ไม่เคยมากกว่า `storage` |
| `volume` | float/int/null | 4 | null 4 รายการ |
| `percent_storage` | float/int | 0 | มีค่าแม้ `volume` เป็น null ทั้ง 4 รายการ |
| `inflow` | float/null | 189 | ไม่มีหน่วยระบุ |
| `outflow` | float/null | 193 | ไม่มีหน่วยระบุ |

`total` ตรงกับจำนวนอ่างเก็บน้ำที่นับได้จริงในทุกวันที่สุ่มตรวจ 13 วัน

### 3.2 ความสัมพันธ์ของค่าในรายงาน (ตรวจกับรายงานปัจจุบัน)

- `percent_storage` เท่ากับ `100 × volume ÷ storage` ตรงทุกรายการที่คำนวณได้ (457 รายการ, ไม่มีรายการใดคลาดเคลื่อนเกิน 0.05 จุดเปอร์เซนต์) จึงใช้ค่าของผู้ให้บริการได้โดยไม่ต้องคำนวณซ้ำ
- `percent_storage` มีค่ามากกว่า 100 อยู่ 90 รายการ และเป็นชุดเดียวกับรายการที่ `volume > storage` ทั้ง 90 รายการ → เป็นข้อมูลที่ผู้ให้บริการให้มาเอง **ห้ามตัดค่าที่ 100**
- `volume < dead_storage` มี 3 รายการ (อ่างที่ระดับน้ำต่ำกว่าปริมาณเก็บกักขั้นต่ำสุด) เป็นสัญญาณภัยแล้งที่ถูกต้อง ไม่ใช่ค่าผิด
- `volume` เป็น null 4 รายการ แต่ `percent_storage` ยังมีค่า → ห้ามคำนวณ `percent_storage` ทดแทนจาก `volume` เมื่อ `volume` หาย

## 4. Grain และขอบเขตเชิงพื้นที่

- **grain จริง:** หนึ่งระเบียนต่อ (วันที่รายงาน, รหัสอ่างเก็บน้ำ) — 461 อ่างต่อวัน
- **การจัดกลุ่ม:** `region` เป็น 6 ภาคแบบ macroregion (ภาคเหนือ / ตะวันออกเฉียงเหนือ / ตะวันออก / กลาง / ตะวันตก / ใต้)
  **ภาคไม่ใช่จังหวัด** และไม่ใช่รหัส 77 จังหวัด
- **ไม่มีใน payload:** รหัสจังหวัด, พิกัด, ลุ่มน้ำ, ระดับน้ำทะเล, เวลาที่เผยแพร่รายงาน
- **อัตลักษณ์อ่างเก็บน้ำ:** `id` รูปแบบ `rsv` + ตัวเลข ไม่ใช่รหัสต้นทางที่มีความหมายเชิงพื้นที่
- **ขอบเขต:** เป็นเฉพาะอ่างขนาดกลางที่ RID แจ้งไว้ ไม่ใช่อ่างเก็บน้ำทุกแห่งในประเทศ

ข้อสรุปตามกติกาโปรเจกต์: ยังสร้างตัวชี้วัดระดับจังหวัดจากแหล่งนี้ไม่ได้
ต้องมีตารางเชื่อมอ่าง→จังหวัด/พิกัดจากผู้ให้บริการก่อน และห้ามใช้ภาคแทนจังหวัด

## 5. หน่วยข้อมูล (จากหน้าเอกสารทางการ)

หน้าเอกสาร `https://app.rid.go.th/reservoir/api/document/reservoir` ระบุไว้ดังนี้ (คัดตามต้นฉบับ)

| ฟิลด์ | คำอธิบายในเอกสาร | หน่วยที่ยืนยันได้ |
|---|---|---|
| `date` | วันที่ | วัน (ISO `YYYY-MM-DD`) |
| `total` | จำนวนอ่างเก็บน้ำ | จำนวน |
| `region` | ภาค | ข้อความภาค |
| `id` | รหัสอ่างเก็บน้ำ | รหัส |
| `name` | ชื่ออ่างเก็บน้ำ | ข้อความ |
| `storage` | ปริมาณน้ำเก็บกัก | **ล้าน ลบ.ม.** (ล้านลูกบาศก์เมตร) |
| `dead_storage` | ปริมาณน้ำเก็บกักต่ำสุด | **ล้าน ลบ.ม.** |
| `volume` | ปริมาณน้ำในอ่าง | **ล้าน ลบ.ม.** |
| `percent_storage` | เปอร์เซนต์ปริมาณน้ำต่อปริมาณกักเก็บ (ปัจจุบัน) | **เปอร์เซนต์** (ไม่มีหน่วยย่อยระบุ) |
| `inflow` | ปริมาณน้ำไหลเข้าอ่าง | **ไม่มีหน่วยระบุ** |
| `outflow` | ปริมาณน้ำระบาย | **ไม่มีหน่วยระบุ** |

ผู้ให้บริการระบุไว้ท้ายหน้าเอกสารว่า "ศูนย์ปฏิบัติการน้ำอัจฉริยะ กรมชลประทาน"

**ข้อควรระวังเรื่องหน่วย:** หน่วยของ `inflow`/`outflow` ไม่ปรากฏในเอกสารที่เข้าถึงได้
ค่าที่สังเกตมีขนาดเล็กกว่าหน่วยล้าน ลบ.ม. มาก จึงสงสัยว่าเป็นอัตราการไหล (เช่น ลบ.ม./วินาที)
แต่ **ยังยืนยันไม่ได้** จึงต้องเก็บเป็นค่าดิบที่ไม่ทราบหน่วย และห้ามนำไปคำนวณ balance
หรือเปรียบเทียบข้ามอ่างจนกว่าจะได้คำยืนยันหน่วยจาก RID/SWOC

## 6. การ query วันที่ย้อนหลังและข้อจำกัด

### 6.1 รูปแบบที่ใช้ได้

หน้าเอกสารทางการระบุ endpoint ย้อนหลังไว้เอง (`.../public/2022-01-09`)
การตรวจยืนยันว่าใช้ได้จริงและเนื้อหาเปลี่ยนตามวันที่ (เทียบลายเซ็น SHA-256 ของค่าทั้งรายงาน)

| รูปแบบที่เรียก | ผล |
|---|---|
| `/public/YYYY-MM-DD` | ใช้ได้ คืนรายงานของวันนั้นจริง |
| `/public?date=YYYY-MM-DD` | **ไม่มีผล** คืนรายงานปัจจุบัน (query parameter ถูกเมิน) |
| `/public?from_date=YYYY-MM-DD` | **ไม่มีผล** คืนรายงานปัจจุบัน |
| `/public?region=...` | ไม่มีผล ไม่มีการกรอง เอกสารไม่ระบุ query parameter |
| `/public/` (ขึ้นบรรทัดใหม่) | คืนรายงานปัจจุบัน |

### 6.2 ขอบเขตประวัติที่ตรวจได้

- ตรวจแบบสุ่มวันที่ทุก 30 วันตั้งแต่ 1998-01-15 ถึง 2026-10-24 จำนวน 351 วัน → ตอบสำเร็จ 351 ครั้ง
  ไม่พบวันที่ใดที่ได้เนื้อหาซ้ำกับตัวอย่างก่อนหน้า และไม่พบ error
  → สนับสนุนว่า **ประวัติต่อเนื่องรายวันตั้งแต่ 1998-01-01 ถึงปัจจุบัน**
  (การตรวจนี้เป็นการสุ่มทุก 30 วัน ไม่ได้ยิงทุกวันของช่วง 28 ปี ต้องยืนยันความต่อเนื่องรายวัน
  เต็มรูปแบบอีกครั้งตอนทำ backfill จริง)
- วันที่ก่อน 1998-01-01 ทุกวันคืนเนื้อหาเดียวกัน (รายงานเก่าสุดที่มี) แต่เขียนป้าย `date` ตามวันที่ที่ขอ
- รายงานปัจจุบันเผยแพร่ในวันเดียวกัน (ตรวจเมื่อ 24 ต.ค. 2569 ได้ `date = 2026-10-24`)

### 6.3 พฤติกรรมกรณีขอผิด (ต้องระวังใน connector)

| เคส | ผลการตอบ | ความเสี่ยง |
|---|---|---|
| วันที่อนาคต เช่น `2030-01-01` | HTTP 400 body `"Field is invalid date"` | ตรวจสอบสถานะ HTTP ได้ |
| รูปแบบผิด เช่น `not-a-date` หรือ `20260101` | HTTP 400 body `"Field is invalid date"` | ตรวจสอบสถานะ HTTP ได้ |
| วันที่ไม่มีจริงในปฏิทิน เช่น `2026-02-30` | **HTTP 200 แต่คืนรายงานปัจจุบัน** | เงียบ ได้ข้อมูลผิดวัน |
| วันที่ก่อน 1998-01-01 | **HTTP 200 คืนรายงานเก่าสุดที่มี พร้อมเขียนป้าย `date` ตามวันที่ที่ขอ** | เงียบ ได้ข้อมูลผิดวัน |

สองเคสหลังเป็นกับดักหลักของงานนี้ เพราะ **`date` ใน payload ถูกเขียนทับตามวันที่ที่ขอเสมอ
จึงตรวจจับได้จากป้ายวันที่อย่างเดียวไม่ได้** ต้องตรวจเนื้อหาจริงด้วย

**ข้อเสนอแนะสำหรับ connector (M4/M5):**

1. เรียกด้วย path form เท่านั้น และตรวจ `payload.date == วันที่ที่ขอ` ทุกครั้ง
2. เพิ่มการตรวจเนื้อหาด้วยลายเซ็น (SHA-256 ของชุดค่าทั้งรายงาน) เทียบกับรายงานปัจจุบัน
   เพื่อจับกรณีที่ endpoint คืนรายงานอื่นแบบเงียบ (ค่านี้เพิ่มใน `scripts/probe_rid_api.py` แล้ว)
3. ปฏิเสธวันที่ก่อน 1998-01-01 และวันที่ในอนาคตก่อนออก request
4. ตรวจสอบกับ `src/tadih/reservoirs.py` ที่มีอยู่แล้ว: ฟังก์ชัน `_records()` ตรวจ `report_date != requested_date`
   ซึ่งจับกรณีวันที่ไม่มีจริงในปฏิทินได้ แต่ **ยังจับกรณีวันที่ก่อน 1998 ไม่ได้** เพราะป้าย `date` ถูกเขียนทับ
   → ต้องแจ้ง integrator เพิ่มการตรวจช่วงวันและลายเซ็นก่อนเปิดใช้งานจริง

## 7. สิทธิ์และการเผยแพร่ต่อ (license)

ค้นข้อความสิทธิ์ในหน้าเอกสารทางการและหน้าแรกของ `app.rid.go.th` ด้วยคำค้น
copyright, license, licence, สิทธิ์, ลิขสิทธิ์, creative commons, cc by, เงื่อนไข, เผยแพร่, reuse,
พระราชบัญญัติ, copyleft → **ไม่พบข้อความใดเลย (0 ครั้งทุกคำค้น)**
หน้าเอกสารมีเพียงชื่อผู้ให้บริการ ("ศูนย์ปฏิบัติการน้ำอัจฉริยะ กรมชลประทาน") ซึ่งเป็นการระบุแหล่งที่มา
ไม่ใช่การอนุญาตให้ใช้หรือเผยแพร่ต่อ

**สถานะที่บันทึก:** `license_status = pending` และต้องคงไว้เช่นนี้
ข้อมูลชุดนี้ยังห้ามส่งออกสู่ public API, หน้าเว็บ, props หรือ cache จนกว่าจะมีคำยืนยันสิทธิ์เผยแพร่ต่อ
เป็นลายลักษณ์อักษรจาก RID/SWOC (กติกาเดียวกับที่ระบุใน `source-expansion-api.md`)

## 8. ความต่างระหว่าง endpoint สาธารณะกับ SWOC

| รายการ | `app.rid.go.th` (สาธารณะ) | `swoc-api-service.rid.go.th` |
|---|---|---|
| การยืนยันตัวตน | ไม่ต้องใช้ credential | `security: jwtAuth / BearerAuth` → HTTP 401 |
| ข้อความเมื่อไม่มีสิทธิ์ | — | `{"detail":"ไม่พบข้อมูลการเข้าสู่ระบบ"}` |
| รูปแบบข้อมูล | เหมือนกัน | เหมือนกัน (`document` ชี้ไปหน้าเอกสารเดียวกัน) |
| เอกสาร OpenAPI | เป็น HTML สรุปฟิลด์ | JSON schema สาธารณะที่ `/api/schema/` (อ่านได้โดยไม่ต้อง login) |

ข้อสังเกตจากการเทียบค่าจริงของอ่างเก็บน้ำเดียวกันในวันที่เดียวกัน (`2026-03-13`):
ค่า `storage`, `dead_storage`, `volume` และ `percent_storage` ตรงกับตัวอย่างในเอกสาร OpenAPI ของ SWOC ทุกตัว
แต่ `inflow` และ `outflow` **ไม่ตรงกัน** → ค่าสองฟิลด์หลังเป็นค่าที่เปลี่ยนได้ในภายหลัง
จึงไม่ควรใช้ย้อนหลังแล้วอ้างว่าเป็นค่าของวันนั้นแบบตรวจสอบย้อนหลังได้

อีกจุดคือตัวอย่างในเอกสาร SWOC ระบุจำนวนอ่างเก็บน้ำ `total: 448` ขณะที่ endpoint สาธารณะคืน `461`
สำหรับวันที่เดียวกัน → **ตัวอย่างในเอกสาร SWOC ล้าสมัย ไม่ควรใช้เป็นความจริงเชิงอ้างอิง**
รายการอ่างเก็บน้ำของ endpoint สาธารณะมีจำนวน 461 และชุด id เหมือนกันทุกประการตั้งแต่ 1998-01-01

## 9. สิ่งที่ยังไม่ตรวจและงานที่ต้องรอ

- ยังไม่มีคำยืนยันสิทธิ์เผยแพร่จาก RID/SWOC → `license_status` คง `pending` และห้ามเปิด public
- ยังไม่มีตารางเชื่อมอ่างเก็บน้ำ→จังหวัด/พิกัด/ลุ่มน้ำ → ยังไม่มีตัวชี้วัดระดับจังหวัด
- ยังไม่ยืนยันหน่วยของ `inflow`/`outflow` และช่วงเวลาสะสม → ห้ามคำนวณจากสองฟิลด์นี้
- ยังไม่ทราบเวลาเผยแพร่รายงานและลำดับการทบทวนข้อมูลย้อนหลังของผู้ให้บริการ
- ไม่ทราบขอบเขต "อ่างขนาดกลาง" ที่ครอบคลุมครบทุกแห่งหรือไม่ (ใช้จำนวน 461 ตามที่ผู้ให้บริการแจ้ง)
- ยังไม่ทดสอบพฤติกรรมเมื่อยิงซ้ำถี่หรือมี rate limit → ควรมี backfill แบบจำกัดจำนวนวันและหน่วงเวลา
- ยังไม่ตรวจว่ามี endpoint อื่นของชุดนี้ที่ให้ข้อมูลรายอ่างพร้อมพิกัดหรือไม่

## 10. วิธีรันซ้ำ

```powershell
# รายงานเต็มไปที่ stdout (ไม่บันทึกค่าตัวเลขของอ่างเก็บน้ำ)
python scripts/probe_rid_api.py

# เลือกวันที่เอง
python scripts/probe_rid_api.py --dates 2026-10-23,2026-01-01,1998-01-01,1997-12-31

# บันทึกรายงาน (ไฟล์รายงานมีแค่ชื่อฟิลด์ ชนิดข้อมูล จำนวน สถานะ และลายเซ็น ไม่มีค่าตัวเลข)
python scripts/probe_rid_api.py --out probe-report.json
```

ผลลัพธ์ที่สำคัญในไฟล์รายงาน: `current_report.schema` (โครงสร้างและ grain),
`report_dates[]` (สถานะและลายเซ็นของแต่ละวัน), `content_collisions` (วันที่ที่ถูก clamp),
`date_label_mismatch_dates` (วันที่ที่ได้รายงานอื่นกลับมา),
`official_documentation.license_statement_found` (ยังเป็น `false`) และ `swoc_api.status` (ยังเป็น `401`)
