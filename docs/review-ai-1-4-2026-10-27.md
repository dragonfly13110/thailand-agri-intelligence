### 1. [P1] สองงานเขียน NWP รอบเดียวกันทำให้ข้อมูลคนละเวอร์ชันปนกัน

- จุดที่เกี่ยวข้อง: [sync_tmd_hpc_nwp.py:969](../scripts/sync_tmd_hpc_nwp.py#L969), [sync_tmd_hpc_nwp.py:992](../scripts/sync_tmd_hpc_nwp.py#L992), [sync_tmd_hpc_nwp.py:869](../scripts/sync_tmd_hpc_nwp.py#L869)
- หน้าที่: publisher เขียน snapshots และข้อมูลจังหวัด แล้วเปลี่ยนสถานะ run เป็น ready โดยใช้ hash ช่วยตรวจเวอร์ชัน
- ปัญหา: child upserts ไม่ผูกกับ hash/เจ้าของงานที่กำลังเขียน และ finalize แบบมีเงื่อนไขไม่ตรวจว่า UPDATE สำเร็จหรือไม่ หากงาน A และ B เขียน run ID เดียวกันแต่ payload ต่างเวอร์ชัน งาน B อาจเขียนและ finalize เสร็จก่อน จากนั้นงาน A ที่ค้างอยู่ยังเขียนค่าจังหวัดของตัวเองทับ และรายงาน `written` แม้ finalize ของ A ไม่ได้เปลี่ยนสถานะ
- หลักฐาน: จำลองลำดับดังกล่าวบน SQLite โดยใช้ schema จริง ผล run เป็น `ready`, grid ของรุ่นใหม่ = `99.0`, แต่ข้อมูลจังหวัดเป็น `[12.5, 12.5]` ของรุ่นเก่าแทน `[99.0, 99.0]` เมื่อ retry รุ่นใหม่อีกครั้งกลับได้ `skipped_identical` เพราะจำนวน child rows ยังครบ ดู `.tmp_qa/review-agents-1-4/nwp-race.py` และ `nwp-race.jsonl`
- แนวแก้: ทำให้แต่ละ child write, การ finalize และการ mark failed ผูกกับเจ้าของ/เวอร์ชันที่ยังถือสิทธิ์เขียนจริง พร้อมตรวจผลว่ามีแถวถูกอัปเดต หาก ownership เปลี่ยนต้องหยุดและรายงานล้มเหลว ไม่เปิด run ที่อาจมีข้อมูลปน; เพิ่ม regression test สอง publisher ที่สลับจังหวะเขียน
- ผลกระทบ: ถ้า sync หรือ republish รอบเดียวกันต่างเวอร์ชันซ้อนกัน API อาจแสดง grid กับจังหวัดจากคนละรุ่นในสถานะพร้อมใช้ แม้ทดสอบ retry แบบทีละงานผ่านแล้ว
- ขอบเขตหลักฐาน: เป็น failure simulation ใน SQLite ไม่ได้เขียนหรือทำให้ D1 จริงเสียหาย ยังไม่มีหลักฐานว่ารอบที่เผยแพร่อยู่จริงปนกัน
